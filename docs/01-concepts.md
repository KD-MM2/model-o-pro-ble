# 01 — Concepts: what we are doing and why it works

## 1. The hardware

* **Mouse:** Glorious Model O Pro Wireless, MCU **Nordic nRF52840** (1 MB flash, 256 KB RAM).
* **Radio:** one 2.4 GHz radio. The stock firmware uses it with direct register access for
  Glorious's proprietary dongle protocol. BLE needs Nordic's **SoftDevice**, which owns the
  radio exclusively. So BLE and the proprietary dongle link are **mutually exclusive at
  runtime**: the mouse boots into one mode (stored in flash) and a button chord switches.
* **Sensor:** PixArt, on SPI2 (SCK P0.12, MOSI P0.8, MISO P0.11, motion IRQ P0.6).
* **Buttons** (active low): LEFT P1.15, RIGHT P1.13, MIDDLE P1.10, BACK P0.9, FORWARD P0.10,
  DPI P1.0. Wheel encoder A P0.2 / B P0.29.
* **RGB LED:** PWM0 on P0.13 (R), P0.15 (G), P0.17 (B).

## 2. The stock firmware

* The vendor app is a **flat 93 328-byte image, linked for 0x6000** (0x6000–0x1CC8F), ~100 %
  Nordic nRF5 SDK 17-style code. It was built as a *SoftDevice-first* program: it contains the
  whole BLE host stack glue (`nrf_sdh`, peer manager, GATT, `ble_bas`, a CLI, device name
  "Model O PRO Wireless") and all 39 distinct `SVC` numbers it uses match the official S140
  ABI. But the product never shipped a SoftDevice, so the BLE paths were dormant: a flag byte
  at `0x20003830` is 0 ("no SoftDevice") and the app then drives clocks/USB power directly.
* It never calls `sd_ble_enable` (SVC 0x60) or `sd_ble_cfg_set` (SVC 0x69), so merely adding a
  SoftDevice is not enough: we must also enable it and register our own GATT services.
* Mouse-report pipeline (original addresses, i.e. flash address − 0x21000 after relocation):

  ```
  1 ms timer tick (TIMER1 handler 0x18BA4)  ──> button scan 0x16B0C ──> macro/remap engine 0xE32C
  motion task 0x1319C  ──> accumulators 0x20003016 (X), 0x20003018 (Y)
  main loop ──> report builder 0x14CEC  (when bit2 of 0x2000300C is set)
       fills the USB EPIN1 buffer @0x200035E5:
         [0] buttons  [1] wheel  [2:3] X (int16)  [4:5] Y (int16)  [6] pan
       then calls the transport at 0x14DC8 (`bl 0x15E5C`), returning 1 on success
       on success it clears the accumulators
  ```
  That `bl 0x15E5C` call is where we hook in: "try USB, else BLE".
* A vendor-mode variable `[0x20003003]` is set to 1 once at boot (by the code around orig
  0xE880). The transport dispatches on it: 1 = USB/BLE leg, 2 selects the 2.4 GHz radio path (`0x9084`), which this product does not use for the
  wired/BLE path.

## 3. The plan

```
 0x00000  ┌──────────────────────────────┐
          │ Nordic MBR  (0x0–0xB00)      │   installed from the S140 hex
 0x01000  ├──────────────────────────────┤
          │ SoftDevice S140 7.3.0        │   0x1000–0x26497, never modified
 0x27000  ├──────────────────────────────┤
          │ vendor app, RELOCATED        │   stock 0x6000 image shifted by +0x21000
          │  (hooks patched in)          │   ends at 0x3E207
 0x3F000  │ STUB, THUNKs (assembly)      │   generated by tools/mk_ble.py
 0x40000  │ blehid blob (C)              │   built from fw/blehid/blehid.c, ~8 KB
 0x8B000  │ vendor settings (2 pages)    │   0x8B000/0x8C000 – preserved, never written by us
 0xFD000  │ bond area (4 host slots)     │   written by blehid
 0xFE000  │ mode/config record (1 page)  │   written by blehid
          └──────────────────────────────┘
```

Three jobs:

1. **Relocate the app** from 0x6000 to 0x27000 because the SoftDevice occupies 0x1000–0x26497.
   With no source and no relocation table this is a binary rebase (`tools/relocate.py`), see
   [07-internals](07-internals.md#2-relocation).
2. **Bring the SoftDevice up** early in the app's boot (a stub hooked at `0xE878`+D), enable
   BLE, register services, start advertising.
3. **Forward the stock report** into a GATT HID notification
   (`blehid_tx_stock`), and route a few stock behaviours around SoftDevice restrictions.

Because the SoftDevice runs, *the app must stop poking peripherals the SoftDevice owns*
(POWER, NVMC, RADIO and the NVIC lines for the radio): an app access to those faults with
id `0x1001` (APP_MEMACC). Each such access in the stock code is replaced with the SoftDevice's
SVC equivalent or gated off ([07-internals §4](07-internals.md#4-patch-table)).

## 4. Modes and who is in charge

| Condition | Transport used |
|---|---|
| USB cable plugged (stock "direct USB" flag `[0x200035DE]==1`) | USB (always wins) |
| No USB, mode record = BLE (default) | BLE through the SoftDevice |
| Mode record = DONGLE | SoftDevice is **not** enabled; the vendor 2.4 GHz path runs unmodified |

The mode lives in flash page `0xFE000`: `{C0DE0001, mode, ~mode, generation}`. The stub reads
it at boot; the BLE module rewrites it when you hold the mode chord.

## 5. Reference material that guided the work

* The **Model O3 Wireless** firmware (same MCU, 3 modes) was disassembled as *behavioural
  reference only* (HID descriptor layout, GAP name/appearance). Nothing was transplanted; its
  event-bus framework differs too much. Its notes are in
  [appendix/worklog-raw.md](appendix/worklog-raw.md) (UPDATE 5–6).
* Nordic S140 7.3.0 API headers (`fw/sd_api/`).
